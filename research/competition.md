# Personal AI usage tracker competitive research

Research date: September 13, 2026. Primary product websites, public repositories, Apple App Store listings, issue reports, and release notes were opened. Product features below are vendor/maintainer claims, not results of installing and benchmarking the apps. Repository main branches can lead released binaries. Price snapshots are regional and can change. Issue anecdotes establish failure modes, not prevalence, market share, or present-day defects.

## Finding that changes the strategy

The proposed combination of a Mac menu-bar quota tracker, iPhone companion, GitHub-style activity grid, provider switching, reset alerts, and pace forecasts already exists across several products. Even uncertainty-aware forecasts and data-source labels are appearing. A defensible project needs demonstrably better reliability, faster recovery, clearer limits, and a workflow users prefer. “All models in one place” and “GitHub for tokens” are positioning and design, not sufficient moats.

## Evidence of where implementations have struggled

These are specific historical reports or vendor-acknowledged fixes. They should become acceptance tests, not an assertion that competing products are generally failing.

| Failure class | Dated evidence and status | Requirement to compete well |
| --- | --- | --- |
| Authentication expiry becomes mysterious permanent downtime | [CodexBar #1287](https://github.com/steipete/CodexBar/issues/1287), opened June 3, 2026, **closed**. A user reported recurring expired-session states and unsuccessful delegated CLI refresh, with an unactionable error. The user’s suggested root causes are hypotheses, not verified provider protocol facts. | Distinguish expired login, provider outage, rate-limited polling, missing permission and unsupported plan. Preserve last good data with explicit age and an action that actually repairs the connection. |
| Polling itself becomes unreliable or expensive | [CodexBar #575](https://github.com/steipete/CodexBar/issues/575), March 19, 2026, **closed**, reports generic/silent behavior on Claude 429 responses. [CodexBar changelog](https://raw.githubusercontent.com/steipete/CodexBar/main/CHANGELOG.md), version 0.30.1 May 28, documents caching credentials and backing off 429 retries. | Per-provider backoff/jitter, one refresh owner, coalesced requests, no token-deletion reflex on 429, and no multiplying polls across devices. |
| Local reports omit other devices | [Claude Code Usage Monitor #152](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/152), September 1, 2025, displayed **open**. One user with Windows and Mac reported separate local totals and inaccurate account prediction. Current v4 has since added official statusline input and multisource paths, so the old complaint cannot characterize all current modes. | Keep account-wide quota separate from local-device activity; expose coverage. Deduplicate historical events if syncing/importing logs. |
| Forked session history is charged twice | [ccusage #988](https://github.com/ccusage/ccusage/issues/988), May 12, 2026, **closed**, references fixes #989/#1156. Reporter used @ccusage/codex 18.0.11 and observed large jumps after branching Codex Desktop conversations. | Versioned parser fixtures for parent/child forks, inherited prefixes, cumulative counter resets, compaction, imports and cross-device duplicates. Store stable event identity and attribution time. |
| Battery and history correctness regressions | [SessionWatcher release notes](https://sessionwatcher.com/releases): August 5 fixed repeated full-session scans, fast expired-token polling and helper restart loops; August 25 fixed reporting only a day’s busiest session instead of summing sessions; August 30 fixed history-loss paths on failed writes/unreadable files. These are vendor-acknowledged **fixed** defects, not independent benchmarks. | Incremental ingestion, bounded helper lifecycle, idle/signed-out energy benchmarks, atomic durable history, and clear definitions for aggregated quota percentages. |

## Crowded territory versus hypotheses worth testing

Already implemented somewhere in this sample: multi-provider menu bar; five-hour and weekly countdowns; tokens/API-equivalent spend; model/project breakdowns; GitHub activity grid; pace/burndown; “which tool still has headroom”; low-limit/reset notifications; iCloud sync; native mobile/Watch; direct mobile login; source/freshness labels; uncertainty-aware projections; local-only privacy; multiple accounts; standalone CLI outputs.

Potentially stronger hypotheses, subject to user validation and hands-on competitor tests:

1. **A reliability contract users can inspect.** Publish measured connection uptime, dashboard agreement and stale-reading rates by provider/source/version. Make the freshness and source state conspicuous at the moment someone decides whether to start work. A green bar with old data should never look available.
2. **A planning experience built around work.** Let users declare a two-hour work block and an upcoming deadline; present a conservative capacity range and eligible alternatives with user-defined capability requirements. Test whether this changes decisions and avoids disruption better than existing pace lines. Do not promise a specific task’s token cost from its title.
3. **Cross-device correctness with minimal secrets.** Investigate a desktop collector plus encrypted normalized snapshots, deterministic account IDs, event deduplication and explicit source coverage. This is an architectural proposition, not novel simply because it syncs. Mobile direct access where legitimately supported can improve desktop-off behavior.
4. **Fast, honest recovery.** Count time-to-first-correct-reading and time-to-reconnect after token expiry, sleep, VPN/network changes and a provider format change. Compare against actual installed competitors with the same accounts. Show contextual help rather than API jargon.
5. **A useful private activity record.** GitHub-inspired density can help reveal patterns, but a heatmap should reward completed work or healthy planning rather than raw token burning. Offer annotations and outcome tags without ingesting prompts/source code by default.

Suggested benchmark suite: 30-minute first-run setup sessions with non-experts; seven-day side-by-side quota comparisons; refresh-token expiry/revocation; 429 with Retry-After; malformed/missing fields; provider schema change; weekly rollover and timezone/DST changes; no active five-hour window; model-specific and shared pools; manual credits; two accounts; two Macs + iPhone; sleeping/offline desktop; cloud sessions absent from local logs; branched logs; unknown model pricing; notification permission denied; battery cost while idle/active/signed out; partial/damaged history writes. Log a failure category and remediation time for each.

## Commercial reading

Free open-source competitors constrain the price of a basic meter. SessionWatcher provides a concrete public paid anchor; AI Session Meter’s low one-time unlock adds pressure for Apple-only feature bundles. These prices demonstrate offers, not conversion rates or a large addressable market. Paid differentiation should be validated against saved interruption time, durable history, cross-device dependability and support. Do not infer business success from GitHub stars, testimonials, or vendor user counts.

The threat also comes from existing providers adding their own meters. A portfolio that helps users coordinate several subscriptions could retain value, but the underlying data access can remain fragile. The integration matrix and support budget are core product work, not cleanup after the UI ships.
