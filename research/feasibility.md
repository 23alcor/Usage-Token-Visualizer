# Platform and Claude integration feasibility

Research verified September 13, 2026. This is a primary-source documentation review; no provider connection or native prototype was tested. Architectural recommendations are explicitly identified as inferences. Provider documentation changes rapidly, so retain a tested-version compatibility matrix.

## Highest-impact findings

**There is now a documented Claude Code route for quota snapshots.** Claude Code v2.1.251+ can pass `rate_limits.five_hour` and `rate_limits.seven_day` to a user-configured status-line command. Each supplies `used_percentage` and `resets_at`. These fields are available for Pro/Max subscribers after the session’s first API response; windows can be independently absent and are removed when their reset time passes. A gateway-specific spend limit is a separate possibility. The status-line command runs locally without using API tokens. Its context token fields describe the current context rather than lifetime usage, and its session dollar amount is a client-side estimate. [Claude Code status-line documentation](https://code.claude.com/docs/en/statusline)

**Treat iOS as a companion to a collector, not a universal passive collector.** Apple says third-party apps are sandboxed and can obtain other apps’ information only through explicitly provided system services. Consequently, an ordinary standalone tracker cannot silently read the Claude or ChatGPT native app’s private usage records. This is an architectural inference from Apple’s documented sandbox, rather than a claim that every possible user-mediated workflow is impossible. [Apple runtime security](https://support.apple.com/guide/security/security-of-runtime-process-sec15bfe098e/web)

**Do not make copied Claude subscription credentials the core commercial dependency.** Anthropic’s current developer guidance says third-party developers may not offer Claude.ai login in their own apps or collect, store, or intermediate Claude.ai credentials/session tokens. It distinguishes these from customer-managed API keys. It allows end users to sign into an unmodified Claude Code binary through Anthropic’s flow. The document also constrains brand/name use and points authentication questions to sales. This is a material product dependency; the recommendation is to build on supported local exports and obtain written clarification before shipping any connector that depends on subscription credentials. This is not a legal determination about a specific competing product. [Anthropic authentication and credential guidance](https://code.claude.com/docs/en/legal-and-compliance)

## What Claude actually measures

- Claude’s help center distinguishes time-period usage limits from conversation-length/context limits. Usage depends on conversation length/complexity, features, model, and effort. Claude.ai, Claude Code, and Claude Desktop contribute toward shared usage limits. Do not translate a context-window percentage into remaining subscription quota. [How usage and length limits work](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work)
- Paid-plan Usage settings expose five-hour session progress, weekly limits, and reset timing; some usage-based Enterprise plans instead charge on consumption. The help center describes model/effort/tool/file factors and caching benefits. Product implication: preserve provider-defined buckets and labels instead of forcing every plan into one five-hour counter. [Usage-limit best practices](https://support.claude.com/en/articles/9797557-usage-limit-best-practices)
- Claude Code offers opt-in OpenTelemetry metrics including token counts, estimated costs, model, input/output/cache categories, and main/subagent/auxiliary attribution. Prompt content and tool details are not logged by default; user identity can appear in exported attributes. Metrics can support privacy-preserving analysis if the collector keeps sensitive logging disabled and strips unneeded identity. Cost estimates should be reconciled against provider billing when relevant. A documented historical bug inflated progressively streamed usage before v2.1.214, illustrating why source version matters for historical comparisons. [Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage)
- The Claude Console Usage and Cost Admin API concerns organizational API usage, not an ordinary Pro/Max subscription allowance. Admin credentials are required; workspace-scoped API keys do not work. Individual accounts cannot use the Admin API. Token data can use minute/hour/day buckets, while cost data uses daily buckets. Data typically appears within five minutes, sometimes later; sustained polling once per minute is supported. Claude Enterprise uses a different Analytics API/key path. [Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)

## Platform constraints and practical choices

| Platform/surface | Documented capability or constraint | Product implication (inference) |
|---|---|---|
| macOS menu-bar app | A sandboxed app can access user-selected files and retain access; sandboxing is required for Mac App Store submission. | Prefer a small local collector receiving supported exports. If reading logs, ask for the specific folder and persist scoped access. Prototype sandbox compatibility before committing to distribution. |
| Direct Mac distribution | Apple provides Developer ID signing, hardened-runtime guidance, and notarization for outside-store distribution. | A notarized direct Mac release can be an early distribution option, but it does not authorize provider-credential reuse. |
| iOS foreground app | The app can work with its own data and supported services; it cannot freely inspect another app’s private storage. | Paired usage dashboard, supported API connections, user-triggered imports, and reset/threshold notifications. Clearly show when the desktop collector last reported. |
| iOS widgets | Widget extensions are not continuously active. Frequently viewed widgets typically receive 40–70 refreshes per day, with variable intervals around 15–60 minutes. Timeline entries should be roughly five minutes apart or more. | Display a timestamped quota snapshot and derive a reset countdown from known time locally. Do not promise a continuously live quota percentage. |
| iOS background tasks | The system chooses when background refresh runs, with up to 30 seconds of runtime. Background push delivery is also system-controlled. | Refresh opportunistically/on foreground; schedule from authoritative reset timestamps and design honestly for stale data. |
| Safari extension | Safari web extensions work on Apple platforms, and website access is permission-controlled. | Browser activity is an additional scoped integration surface, not native-app coverage. A visible usage-page import could be explored after provider-policy review; DOM extraction is fragile. |
| Android | Android isolates app data. WorkManager periodic tasks have a 15-minute minimum interval and do not provide exact scheduling. | Reuse the companion architecture. Extra OS usage permissions are not equivalent to a provider token ledger. |

Table sources: [macOS file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), [sandbox requirement](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox), [Developer ID and notarization](https://developer.apple.com/developer-id/), [Apple runtime security](https://support.apple.com/guide/security/security-of-runtime-process-sec15bfe098e/web), [WidgetKit updates](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date/), [background strategies](https://developer.apple.com/documentation/BackgroundTasks/choosing-background-strategies-for-your-app), [Safari extensions](https://developer.apple.com/safari/extensions/), [Safari permissions](https://developer.apple.com/documentation/safariservices/adjusting-website-access-permissions), [Android sandbox](https://source.android.com/docs/security/app-sandbox), [WorkManager scheduling](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

## Architecture recommendations to differentiate on reliability

The following are design proposals, not claims that providers promise this product functionality:

1. **Separate account-level quota snapshots from event-level token consumption.** A snapshot should contain provider, account, plan/bucket, percent used, reset timestamp, observed timestamp, source, source version, and confidence. A token event should contain a stable event ID, model, time, token categories, project, and optional estimated/billed money. Never add account quota snapshots from two laptops together.
2. **Make missing and stale data visible.** `unknown`, `unavailable`, `stale`, and `estimated` are meaningful states. A passed reset timestamp does not prove a fresh zero-percent reading. Keep a recent observation, show “reset expected,” and reconcile after the next authoritative update.
3. **Use local aggregation with minimal synchronization.** Retain raw histories locally by default. Send only normalized totals/snapshots to the phone if the user enables sync. Keep conversation text, filesystem paths, and repository identities out of sync unless needed and explicitly selected.
4. **Preserve existing developer setup.** Installation of a status-line adapter should chain or integrate with the user’s current status-line command, document the change, and support one-click removal. Avoid silently replacing their customization.
5. **Treat forecasting as a measured estimate.** Learn burn rates separately by model/effort/tool/context conditions and publish an interval, e.g. “at this pace: 40–65 minutes.” Do not promise fixed tokens remaining when the provider only exposes an opaque percentage.
6. **Make adapter quality a product feature.** Show official export/API vs estimated/manual source, version support, last successful read, failure reason, and repair instructions. Retain fixture-based regression tests for schema changes, missing windows, resets, duplicate/multi-device events, DST/time zones, and stale phone snapshots.
7. **Store app-owned secrets using platform facilities.** Apple Keychain stores small secrets in an encrypted database. Use it for the tracker’s own pairing keys or properly supported API credentials; that storage mechanism does not make a prohibited credential integration permissible. [Apple Keychain](https://developer.apple.com/documentation/Security/keychain-services)

## Bounded validation work before building the full product

Test the supported Claude status-line export with one Pro account and one Max account across active use, idle use, two concurrent sessions, and an actual reset; compare against the provider’s Usage page without manufacturing a reset. Verify the product’s minimum Claude Code version. Test whether an active supported export sees account usage made on other devices promptly enough for the promised experience. Measure widget freshness over several days with the Mac asleep and disconnected. Prototype the Mac collector under sandbox rules and decide the distribution channel based on demonstrated requirements. Finally, ask Anthropic for confirmation of the intended telemetry-only integration and any planned browser connector.

These are prerequisites for claiming “automatic across devices.” Documentation establishes a promising path; it does not yet prove end-to-end coverage or delivery timing.
